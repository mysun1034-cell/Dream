공개

지식 목표

팀 GitHub 레포에 Collaborator를 추가하는 방식과 fork 기반 협업의 차이를 설명하고, 팀 프로젝트에 Collaborator 방식이 더 적합한 이유를 말할 수 있다. `clone → feature branch → push → PR → merge` 협업 흐름의 각 단계가 왜 필요한지 설명할 수 있다 (특히 main에 직접 push하지 않는 이유). 브랜치 네이밍 컨벤션(`feat/`, `fix/`, `docs/`)의 목적을 설명하고 팀 합의 규칙을 직접 만들 수 있다. 데이터셋 탐색 시 샘플 수·특성 수·결측치 여부·타깃 변수 명확성을 기준으로 적합성을 판단할 수 있다. 분류 문제와 회귀 문제의 차이를 설명하고, 선택한 데이터셋이 어느 쪽인지 근거와 함께 말할 수 있다

기능 목표

팀 GitHub 레포를 생성하고 팀원을 Collaborator로 초대할 수 있다. `git switch -c feat/이름-기능명`으로 feature branch를 만들고, 작업 후 `push → PR 열기 → merge` 흐름을 완성할 수 있다. `.gitignore`에 `data/*.csv`, `.venv/`, `.ipynb_checkpoints/`를 추가해 불필요한 파일 추적을 방지할 수 있다. `python -m venv .venv && pip install -r requirements.txt`로 팀 공용 가상환경을 세팅할 수 있다. `project-brief.md`를 작성하고 GitHub에 커밋·PR·merge까지 완료할 수 있다
