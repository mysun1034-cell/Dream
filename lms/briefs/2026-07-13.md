지식 목표

오늘은 '기획을 멈추고 공학을 시작하는' 설계와 계약의 날임을 이해하고, 프론트/백이 독립적으로 병렬 개발하려면 API 계약(URL·Method·요청/응답 JSON·오류 형태)이 100% 일치해야 함을 설명할 수 있다. 책임 분리(React/Controller/Service/Spring AI·Repository), 구조화된 응답(평문이 아니라 JSON), 프롬프트 해부학([역할]+[작업]+[출력 형식]+[사용자 입력]), 단일 테이블 데이터 모델링, 예외 설계(400/500·롤백·키 환경변수)를 설명할 수 있다.

기능 목표

해결할 문제와 사용자를 한 문장으로 정의하고, MoSCoW로 Must 기능 3~5개와 핵심 시나리오를 확정하며, API 계약을 문서화하고, Spring AI 핵심 호출 1개를 구조화 출력(.entity())으로 코드에서 성공시킬 수 있다. 설계로는 Must 3~5개를 잡되 코드로는 그중 1개를 관통시킨다.

산출물 목표

① 문제·사용자 한 문장 정의 ② Must 3~5개 + 핵심 시나리오 ③ 문서화된 API 계약(성공·오류 JSON) ④ 코드로 1회 성공한 Spring AI 핵심 호출(구조화 응답) — 네 가지가 팀 레포/문서에 남는다. '각자 만든 코드가 아니라 연결되어 실행되는 하나의 서비스'가 지향점이다.

기획 확정 — 문제 한 문장 & MoSCoW

해결할 문제와 사용자를 한 문장으로 정의하고, Must 기능 3~5개와 핵심 시나리오를 확정한다.

이 서비스에서 AI가 없으면 안 되는 이유를 한 문장으로 말할 수 있는가?
오늘 코드로 증명할 Must 기능 1개는 무엇인가?

API 계약 문서화 & 책임 분리 설계

프론트/백이 독립적으로 병렬 개발할 수 있도록 API 계약을 문서화하고, 레이어와 DB 스키마를 설계한다.

이 계약만 보고 프론트와 백이 서로 안 기다리고 동시에 개발할 수 있는가?
AI 호출이 실패하면 DB에 반쪽 데이터가 남지 않는가(롤백)?

(가장 중요) Spring AI 핵심 호출 코드 1회 성공

프롬프트 해부학과 구조화 출력으로 핵심 AI 호출 1개를 코드에서 성공시킨다.

응답이 안 오면 무엇부터 확인하는가?(키→모델→프롬프트 출력 형식)
왜 평문 대신 JSON으로 받는가(기업 서비스에 왜 유리한가)?
제출 안내

팀 단위로 남긴다: (1) 문서화된 API 계약(URL·Method·요청/응답/오류 JSON), (2) 코드로 1회 성공한 Spring AI 핵심 호출(구조화 응답, curl/Postman 캡처), (3) MoSCoW 정리(Must 3~5+시나리오)와 DB 스키마, (4) 오늘 작업이 반영된 PR·Project Board. 실제 API Key가 코드·설정에 하드코딩되지 않았는지 점검한다.

다음 수업 연결

내일(Day 3)은 계약 위에서 프론트·백이 병렬로 달린다. React가 오늘 문서화한 계약(예: POST /api/inquiries)을 호출해 구조화 응답을 화면에 렌더링하고, 오늘 설계한 DB 스키마에 실제 저장(Repository)을 붙인다. CORS(React 5173→백엔드 8080)를 준비한다.
