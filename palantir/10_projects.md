# 실전 프로젝트 6종과 포트폴리오 만들기

## 프로젝트의 사용 원칙

여섯 프로젝트는 서로 독립적인 대형 제품 여섯 개를 처음부터 만드는 과제가 아닙니다. 같은 합성 운영 데이터를 사용해 분석→정제→서비스→운영→도입→통합으로 발전시키는 과정입니다. 여기 제공된 코드는 **실행 가능한 참고 구성요소**이며, 모든 확장 요구사항을 완성한 상용 제품은 아닙니다.

각 프로젝트의 제출물에는 구현함, 설계만 함, 아직 검증하지 못함을 구분합니다. 모든 수치·성과는 합성 데이터 또는 직접 수행한 테스트의 결과라고 표시합니다. 실제 사용자 인터뷰를 하지 않았다면 가상 인터뷰 시나리오라고 적습니다.

| 프로젝트 | 선행 강의 | 최종 결과 | DS 핵심 | FDSE 핵심 |
|---|---|---|---|---|
| P01 | 기본 20강 | 지연·누락 KPI와 판단 메모 | 질문·분모·권고 | 같은 계산의 두 구현 |
| P02 | PY-A05, SQL-I07/A05 | 재실행 가능한 이벤트 적재 | 품질 영향·신선도 | 검증·격리·멱등 처리 |
| P03 | PY-A06~09, SQL-A08 | 지점별 운영 조회 API | 업무 흐름·권한 | 계약·보안·테스트 |
| P04 | PY-A01~03 | 설명 가능한 일정 인력 모델 | 가정·제약·채택 | 알고리즘·반례·복잡도 |
| P05 | 중급 이상 | 사용자 도입·의사결정 패키지 | 문제 분해·변화 관리 | 기술 제약 전달 |
| P06 | 전체 | 원천부터 사용자 판단까지 통합 | 효과 검증·설득 | 아키텍처·운영·복구 |

## P01. 지연율을 믿을 수 있는 운영 진단으로 만들기

### 상황과 사용자

지점장은 어느 지점부터 점검할지 알고 싶습니다. 분석 담당자는 전체 방문 수에 지연 방문 수를 나눈 값을 보내 왔습니다. 현장 담당자는 취소와 미기록이 섞여 비교가 불공정하다고 말합니다. 목표는 누구의 말이 맞는지 승자를 정하는 것이 아니라 **공유할 수 있는 지표 계약**을 만드는 것입니다.

### 입력·출력 계약

입력은 branches,visits와 같은 내용의 CSV입니다. grain은 방문 한 건입니다. 지표는 완료·시각 확인 방문을 분모로 하고 10분 초과 지연을 분자로 합니다. 완료 시각 누락은 별도 표시하고, 지점 4의 0건을 보존합니다. 입력에 저장된 세 날 전체를 분석하며 별도 as-of 판정이나 예약 변경 이력은 없습니다.

출력은 지점별 건수·분모·분자·누락·비율, 전체 합계, 지표 정의서, 다음 조사 권고 1쪽입니다. 비율의 평균으로 전체 비율을 만들지 않고 전체 분자/분모를 사용합니다.

### 구현 순서

먼저 행 3개를 손으로 계산합니다. 완료/10분, 완료/15분, 완료/시각 없음이라는 경계를 비교합니다. Python의 `classify_visit`와 `kpi`를 확인하고 같은 계약을 SQL-I10으로 구현합니다. 기본 단계에서는 전체 KPI부터 만들고 지점별 완성본은 중급에서 다시 검토해도 됩니다.

SQL 결과와 Python 결과를 지점 ID로 연결해 비교합니다. 모든 값이 같아야 하며 같지 않으면 CSV와 DB 원천부터 확인합니다. 마지막에 사용자에게 보여 줄 문장을 쓰되, 합성 표본으로 실제 지점의 성과나 원인을 단정하지 않습니다.

### 통과 기준

| 검사 | 기대 결과 |
|---|---|
| 전체 | 24건, 완료 18, 평가 가능 15, 지연 6, 미확인 3 |
| 전체 지연율 | 40% |
| 지점 1/2/3/4 | 50% / 50% / 0% / NULL |
| 10분 정확히 | 지연 아님 |
| 결측 처리 | 정시로 조용히 대체하지 않음 |
| 독립 검증 | Python·SQL·손 계산이 같은 계약으로 일치 |

**참고 코드:** `lab/course_lib.py`, `lab/sql/SQL_I10.sql`, `lab/tests/test_cross_validation.py`. PostgreSQL 판은 `SQL_I10_postgres.sql`이며 제작 환경에서는 미실행입니다.

### DS용 메모의 완성 예시

> 확인 가능한 완료 방문 15건 중 6건이 10분을 초과해 시작했습니다. 완료 18건 중 3건은 실제 시작 시각이 없어 평가하지 못했고 모두 지점 2에 있습니다. 지점 1과 2의 관측 지연율은 각각 50%지만, 지점 2에는 추가 불확실성이 있습니다. 먼저 지점 2의 기록 누락 경로를 확인하고, 두 지점의 지연 방문을 시간대·이동·배정 변경 맥락과 함께 검토하는 것을 제안합니다. 세 날의 합성 자료만으로 인력 부족이 원인이라고 결론 내릴 수는 없습니다.

### 확장 과제

지연 기준을 설정값으로 바꾸고 설정값을 보고서에 기록합니다. 음수 지연은 조기 시작으로 허용할지 원천 오류로 격리할지 정책을 정합니다. 보고 범위의 시작/끝·시간대를 입력받고 경계 테스트를 추가합니다. 같은 템플릿을 지연 대신 취소율에 재사용하되 분모를 그대로 복사하지 않습니다.

## P02. 오류를 숨기지 않는 이벤트 ETL

### 상황과 목표

원천 파일에는 대문자 상태, 공백, 잘못된 ID·날짜, 같은 방문의 새 이벤트가 섞여 있습니다. 작업이 중간에 실패해도 다시 실행할 수 있어야 합니다. 담당자는 왜 어떤 행이 반영되지 않았는지 확인할 수 있어야 합니다.

입력은 `raw_events.csv` 6행입니다. 출력은 별도 DB의 현재 상태 `event_state`, 오류 격리 `quarantine`, 처리 요약입니다. 기본 visits와 ID 체계가 다르므로 자동 병합하지 않습니다.

```bash
# lab/에서 실행. 별도 data/events.db를 생성·갱신함.
python etl.py
python etl.py
```

두 실행 모두 유효 입력 3, 무효 입력 3, 상태 행 2라는 요약을 반환해야 합니다. 이 값에서 유효 입력 수 3과 최종 업무 객체 수 2를 혼동하지 마세요. 같은 방문 101에 두 이벤트가 있기 때문입니다.

### 이미 제공된 참고 구현

`etl.py`는 ID·상태·시각을 정규화하고 나쁜 행을 보관합니다. 갱신 시각과 event_id를 비교해 오래된 상태가 최신 상태를 덮어쓰지 않게 합니다. 같은 파일의 격리 기록은 재실행 때 갱신하여 중복으로 늘리지 않습니다. 한 배치의 상태 변경과 격리 기록은 하나의 트랜잭션에 묶습니다.

이 구현의 event_id 문자열 순서는 동일 시각의 결정적 타이브레이커일 뿐 실제 업무 최신성을 보장하지 않습니다. 또한 원본 정상 이벤트 원장을 모두 저장하거나 같은 event_id의 상충 내용을 검사하지 않습니다. 그 부분이 다음 확장 과제입니다.

### 구현·검증 과제

| 사례 | 최소 기대 결과 | 추가 설명 |
|---|---|---|
| 같은 파일 두 번 | 상태 2행, 격리 3행 유지 | 전체 원본 개수와 상태 개수 구분 |
| 역순 도착 | 오래된 이벤트가 최신 상태를 덮지 않음 | 시간 정규화·버전 의미 확인 |
| 잘못된 ID | 격리, 이유 기록 | 전체 작업을 조용히 성공 처리하지 않음 |
| 같은 버전·다른 내용 | 명시적 충돌 탐지 또는 격리 | 참고 구현에 추가할 요구사항 |
| 적재 중 예외 | 배치의 부분 반영 없음 | 실패 주입 테스트 추가 |
| 원천 파일 이동 | 격리 키 정책 재검토 | 현재 키에 절대 파일 경로가 포함됨 |

제출물은 원천 계약, 상태 갱신 규칙, 실패·재실행 테스트, 격리 행 검토 절차, 제한 사항입니다. DS는 허용 지연과 오류 처리 우선순위를 정하고 FDSE는 코드와 복구 절차를 작성합니다.

**참고 코드:** `lab/etl.py`, `lab/tests/test_core.py`의 재실행 테스트, PY-A05, SQL-A05. 원천 ID·버전 의미를 모른 채 “exactly-once 완성”이라고 적지 않습니다.

## P03. 권한 있는 사용자만 보는 운영 API

### 사용자 행동부터 정의

지점 담당자가 자기 지점의 다음 확인 대상 방문을 조회합니다. 본부 검토자는 여러 지점을 봅니다. 데이터를 볼 수 있는 사람과 변경할 수 있는 사람은 별도 권한입니다. 이번 참고 구현은 읽기만 제공합니다.

### 최소 API 계약

| 항목 | 계약 |
|---|---|
| GET /health | 프로세스 응답 확인. DB 신선도나 전체 의존성 건강을 보장하지 않음 |
| GET /visits | branch_id 필수, after_id 기본 0, limit 기본 20/최대 100 |
| 인증 모사 | X-Demo-Key로 공개된 테스트 주체를 선택 |
| 인가 | 해당 주체의 허용 지점에 요청 지점이 포함되어야 함 |
| 페이지 방식 | visit_id 증가순, 마지막 ID 다음부터 조회 |
| 응답 | 방문 ID·지점·상태·예정 시각만 공개 |
| 오류 | 알 수 없는 키 401, 타 지점 403, 입력 범위 오류 422 |

```bash
python -m pytest tests/test_api.py -q
python -m uvicorn api:app --host 127.0.0.1 --port 8000
```

### 구현 순서와 근거

요청에서 숫자 범위를 먼저 검증합니다. 인증된 주체를 확인하고 그 주체의 허용 지점을 확인합니다. SQL은 값 바인딩을 사용하고 사용자 입력을 문자열로 이어 붙이지 않습니다. 필요한 열만 반환합니다. 페이지의 정렬 기준과 커서 기준이 일치해야 합니다.

고정 합성 데이터에서는 지점 1 첫 두 ID가 1·2이고 after_id=2이면 다음 둘은 3·9입니다. 실제 변경 중인 데이터에서 keyset pagination이 전체 스냅샷을 자동 보장하지는 않습니다. 동시 추가·삭제에 대해 무엇을 보장할지 별도로 정합니다.

### 통과와 확장

기본 통과는 5개 API 테스트입니다. 확장에서는 잘못된 키, 음수 커서, limit 초과, 빈 지점, 마지막 페이지, 다른 지점 접근을 독립적으로 검증합니다. 저장소를 PostgreSQL로 바꾸는 경우에는 DB 드라이버·연결 풀·권한·시간 타입 변환을 새로 테스트합니다.

운영 확장 계획에 실제 인증, 세션·토큰 검증, TLS, 레이트 제한, 요청 ID, 구조화 로그, 의존성 건강 검사, 비밀 관리, 데이터 보관 정책을 적습니다. 공개 데모 키를 실제 보안이라고 설명하지 않습니다.

**참고 코드:** `lab/api.py`, `lab/tests/test_api.py`, PY-A06~09. 인증·인가·SQL 주입 방지는 서로 다른 문제이며 하나가 다른 둘을 자동 해결하지 않습니다.

## P04. 설명 가능한 일정 모델: 몇 명이 동시에 필요한가

### 제한된 문제 정의

동일한 능력의 담당자가 방문 하나를 맡고, 이동·휴식·준비 시간이 0이며, 모든 방문의 시작/끝이 확정되어 있다고 가정합니다. 이 모델에서 최소 필요 인력은 최대 동시 방문 수입니다. 실제 배정 최적화 전체와 다릅니다.

입력은 `(start,end)` 구간 목록이고 `end>start`여야 합니다. 구간은 `[start,end)`입니다. 출력은 필요 인원 정수입니다. PY-A03의 정렬+최소 힙을 구현하고 복잡도 O(n log n)을 설명합니다.

| 입력 | 기대 결과 | 핵심 |
|---|---:|---|
| 빈 목록 | 0 | 빈 입력 |
| (0,10),(10,20) | 1 | 끝과 시작이 같으면 안 겹침 |
| (0,10),(5,15) | 2 | 겹침 |
| (0,100),(10,20),(30,40) | 2 | 중첩과 제거 |
| (10,10) | 오류 | 길이 0 거부 |

### DS 과제

현장 사용자가 위 결과를 신뢰해도 되는 범위를 설명합니다. 자격·이동·휴게·선호·공정성 등 실제 제약 중 무엇이 빠졌는지 인터뷰 질문을 만듭니다. 자동 배정 대신 후보 추천으로 시작할지 결정하고 사용자가 거부 사유를 남기는 흐름을 설계합니다.

### FDSE 과제

최소 인력 수 외에 최대 겹침이 발생한 시각을 반환하도록 확장합니다. 입력 순서를 섞어도 결과가 같은지, 종료와 시작이 같은 경계가 맞는지 테스트합니다. 자격 조건을 추가하면 기존 최적성 주장이 깨지는 반례를 만듭니다. 작은 데이터에서 단순 완전 탐색과 비교하여 새 모델을 검증할 수 있습니다.

**참고 코드:** `lab/examples/PY_A03.py`. 제공 코드는 인원 수만 계산합니다. 완전한 배정표·이동 최적화·실제 업무 자격 검증은 학습자가 확장할 부분입니다.

| 현장 담당자 | 출발부터 늦은 게 아니라 기록 버튼을 늦게 눌러요 | 기록 시각과 실제 시작 시각은 같은가요? 수정 이력은 있나요? |
| 본부 분석가 | 지점끼리 순위를 매겨 주세요 | 업무 난도·시간대·표본·누락이 비교 가능한가요? |

첫 목표는 대시보드 화면 수를 늘리는 것이 아니라 **사용자가 내릴 수 있는 결정 하나**를 명확히 하는 것입니다. 예를 들어 아침 점검에서 기록 누락을 담당자에게 확인하는 흐름은 현재 데이터의 한계 안에서도 시험할 수 있습니다.

### 요구사항 문서의 예

문제: 완료 방문의 시작 시각 누락 때문에 지점 비교와 후속 점검이 불안정하다.

사용자: 지점 운영자와 본부 품질 담당자. 결정: 어떤 누락 방문을 누구에게 확인 요청할 것인가. 제외 범위: 의료 판단, 자동 징계, 실제 인력 법정 기준, 원인이 검증되지 않은 성과 순위.

성공 기준 제안: 확인 대상 목록의 정확성, 담당자의 대상 찾기 성공 여부, 누락 해결까지의 시간, 잘못된 알림 수. 이 값들은 도입 시험에서 측정할 항목이지 현재 교재로 이미 개선했다는 수치가 아니다.

### 도입 실험과 제출물

초기에는 소수의 가상 사용자 역할로 과제를 수행합니다. 사용자에게 클릭 방법을 알려 주기 전에 스스로 누락 방문을 찾아 설명하게 합니다. 실패 지점과 용어 혼동을 기록하고 수정합니다. 실제 사용자가 참여했다면 동의와 조직 정책에 맞게 비식별 기록만 남깁니다.

제출물은 문제 정의 1쪽, 인터뷰 질문 10개, 현재/개선 업무 흐름, KPI 계약, 권한 표, 시범 운영 계획, 교육 안내 1쪽, 실패·재설계 기록입니다. 엔지니어가 구현 가능 여부를 검토할 수 있도록 데이터·시간·규모·보안 제약을 구체화합니다.

### 평가 기준

좋은 결과는 모델·프레임워크 이름의 수가 아니라 문제-데이터-행동의 연결입니다. 사용자가 볼 수만 있고 행동할 수 없다면 다음 흐름을 설명합니다. 실제 영향 평가가 없다면 “모의 워크플로 검증 완료, 실제 현장 효과 미측정”이라고 적습니다.

## P06. 통합 캡스톤: 데이터에서 운영 결정까지

### 시스템 범위

목표는 원천 파일을 검증해 신뢰 가능한 방문 상태·지표를 만들고, 권한 있는 사용자가 근거 행과 품질 상태를 확인하는 흐름입니다. 우선 읽기 경로를 완성하고 그 뒤 별도 복사 DB에서 승인된 상태 변경 Action을 추가합니다.

**중요한 통합 작업:** 제공 `raw_events.csv`에는 client_id·branch_id·예정/실제 시각·금액이 없습니다. 이것만으로 기본 visits를 완전하게 갱신할 수 없습니다. 통합 단계에서는 방문 전체 원천 계약을 정의하고 추가 합성 이벤트를 생성하거나, 안정된 방문 참조 표와 연결하는 방식을 설계해야 합니다. 누락 정보를 추측해 채우지 않습니다.

### 권장 계층과 책임

| 계층 | 책임 | 확인할 실패 |
|---|---|---|
| 원본 보관 | 입력 파일·배치 ID·수신 시각·체크섬 기록 | 파일 중복·손상·원본 유실 |
| 정제 | ID·상태·시간 정규화, 오류 격리 | 잘못된 형식·상충 버전 |
| 업무 표 | 키·상태·이력·수정 규칙 | 중복·참조 누락·구버전 덮어쓰기 |
| 지표 | KPI 계약·품질 경고·기준 시각 | 분모 변화·JOIN 부풀림·오래된 데이터 |
| 서비스 | 인증·인가·요청 검증·제한된 응답 | 타 지점 노출·무제한 요청 |
| 사용자 흐름 | 근거 확인·확인 요청·판단 기록 | 설명 없는 숫자·잘못된 변경 |
| 운영 | 관측·재처리·배포/롤백·감사 | 부분 반영·반복 알림·복구 불가 |

### 단계별 완료 조건

첫째, 수정되지 않은 합성 원본으로 P01의 기준값을 재현합니다. 둘째, 별도 이벤트 공간에서 P02의 재실행을 증명합니다. 셋째, 통합 원천 계약을 추가하고 신규·변경·오류 이벤트가 어떤 표에 반영되는지 설명합니다. 넷째, P03의 권한 검사를 유지한 채 지표 조회를 추가합니다. 다섯째, 동일 입력·권한 실패·시점 경계·부분 실패를 자동화합니다.

마지막으로 사용자 역할 3개에 대해 할 수 있는 일·할 수 없는 일을 시연합니다. 상태 변경을 구현했다면 검증된 사용자, 허용 전이, 버전 충돌, 감사 기록이 함께 처리되어야 합니다. 화면만 있고 서버에서 우회 가능한 권한은 통과가 아닙니다.

### 장애 시나리오 8개

| 사건 | 기대되는 시스템 행동 |
|---|---|
| 잘못된 날짜 | 격리 + 이유 + 전체 품질 상태 반영 |
| 동일 배치 재실행 | 업무 상태 중복 없음 |
| 늦게 온 구버전 | 최신 상태 보호 + 처리 근거 추적 |
| 같은 버전 상충 내용 | 탐지·격리 또는 명시적 충돌 정책 |
| 지점 1 사용자가 지점 2 요청 | 차단, 민감한 본문 미반환 |
| 업데이트 후 감사 저장 실패 | 같은 트랜잭션 변경 롤백 |
| 지표 갱신 실패 | 이전 결과 기준 시각과 경고 표시 |
| 동시 수정 | 버전/잠금 계약에 따라 충돌 처리 |

이 8개는 프로젝트에서 추가로 구현·시연할 요구사항입니다. 제공 기본 API와 테스트 34개가 이 모든 상황을 이미 커버한다고 주장하지 않습니다.

### DS/FDSE 두 가지 최종 발표

DS 발표는 사용자 문제→결정→데이터 신뢰성→제안한 흐름→시범 검증→남은 위험 순서입니다. FDSE 발표는 요구사항→데이터 모델→처리/API 경계→정합성·권한→실패 복구→규모 확장 순서입니다. 둘 다 같은 데모와 검증 결과를 증거로 사용합니다.

### 설계 결정 기록의 작성 예

결정: 첫 버전에서는 지표 계산을 읽기 전용 SQL과 Python 대사로 분리한다. 이유: 작은 데이터에서 규칙 오류를 찾기 쉽고 두 구현의 차이를 설명할 수 있다. 대안: 모든 계산을 API 내부에만 작성한다. 포기한 이유: 업무 정의가 요청 처리 코드에 묻히고 독립 검산이 어렵다. 비용: 같은 규칙을 두 곳에 유지하므로 계약 변경 시 회귀 테스트가 필요하다. 재검토 조건: 데이터 규모·지연 요구가 바뀌거나 중복 유지 비용이 커짐.

### 운영 지침의 작성 예

증상: 지연율이 갑자기 0%로 표시된다. 먼저 분모와 원천 최신 시각을 확인한다. 0건이면 비율 산출 불가인데 0으로 바뀐 것인지 조사한다. 분모가 유지되면 지연 계산·시간대·정규화 변경을 확인한다. 잘못된 배치를 더 배포하지 않고 원본과 마지막 정상 결과를 보관한다. 복구 후 키 집합·건수·합계를 대사하고 사용자에게 영향 범위와 재개 여부를 알린다.

### 정직한 이력서 문장 예시

“합성 방문 운영 데이터를 대상으로 SQL·Python 지표를 교차 검증하고, 재실행 가능한 ETL 및 지점별 접근을 검사하는 로컬 API를 구현했다. 기준 데이터의 지표·경계·오류·권한 테스트를 작성하고 운영 확장 과제를 문서화했다.”

직접 완성하지 않은 통합 기능, 실제 운영 사용자 수, 확인하지 않은 속도 향상, 가상의 고객 성과를 자신의 실적으로 쓰지 않습니다. 제공 예제에서 직접 바꾼 부분과 그 이유가 포트폴리오의 핵심입니다.
