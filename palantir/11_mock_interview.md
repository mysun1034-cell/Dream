# DS·FDSE 문제 분해와 모의 면접 연습

**이 문서의 질문은 교재에서 만든 연습 문제입니다. Palantir의 실제 기출 문제, 내부 면접 절차, 공식 채점 기준이 아닙니다.** 공고에 나타나는 업무 역량을 연습하기 위한 자료이며 특정 질문의 출제를 예측하지 않습니다.

## 1. 모르는 문제를 받았을 때의 공통 틀

먼저 사용자가 누구이고 어떤 결정을 내려야 하는지 확인합니다. 다음에는 성공 기준과 하지 않을 일을 정합니다. 그 뒤 필요한 데이터의 단위·키·시점·누락·접근 권한을 정의합니다. 가장 작은 해결책을 제안하고 정확성·실패·규모를 검증합니다. 마지막에는 사용자 흐름과 도입 후 측정을 설명합니다.

이 순서는 말만 길게 하는 절차가 아닙니다. “지연율 대시보드”를 “아침 점검에서 기록 누락을 발견하고 담당자에게 확인 요청하는 흐름”으로 좁히면 필요한 화면·데이터·API·권한이 구체적으로 달라집니다.

### 첫 질문 6개의 예

| 질문 | 왜 필요한가 |
|---|---|
| 누가 결과를 보고 무엇을 결정하나요? | 보고서와 운영 도구의 목적 구분 |
| 현재는 어떤 방법으로 해결하고 있나요? | 실제 업무 흐름과 대안 이해 |
| 잘못된 결과의 비용은 무엇인가요? | 자동화 범위·사람 확인·안전 기준 |
| 한 행은 무엇이고 고유 ID는 무엇인가요? | 데이터 모델·JOIN 정합성 |
| 정보는 언제 발생하고 언제 알려지나요? | 지표 시점·누수·신선도 |
| 어떤 사용자가 무엇을 볼 수 있나요? | 데이터 접근 경계 |

면접관이 추가 정보를 주지 않으면 작업 가정을 명시하고 진행합니다. 끝없이 질문만 하며 해결책을 내지 않는 것도 피합니다.

## 2. 끝까지 풀어 보는 문제 분해 예시

### 요청: “방문 지연을 줄이는 시스템을 만들어 주세요.”

**사용자와 결정:** 지점 운영자는 당일 기록 누락과 지연 후보를 점검하고 확인 요청을 보냅니다. 본부 담당자는 반복 문제의 유형을 검토합니다. 직원 평가나 자동 불이익 결정은 초기 범위에서 제외합니다.

**먼저 확인할 불확실성:** 실제 시작 시각과 기록 버튼 시각이 같은가, 예정 시각이 나중에 수정되는가, 취소는 어떤 흐름에서 생기는가, 늦은 기록은 정정되는가. 답이 없다면 현재 합성 데이터의 정의만으로 시작하고 원인 분석은 제한합니다.

**데이터:** 방문·고객·지점·담당자, 예정/실제 시각, 상태, 원천 갱신/수신 시각, 권한 관계가 필요합니다. 핵심 grain은 방문이고 변경 이력은 별도 이벤트입니다. 청구는 방문과 직접 연결 키가 없으므로 초기 지연 판단에 억지로 JOIN하지 않습니다.

**최소 해결책:** 유효 완료 방문의 지연율과 결측 목록을 보여 줍니다. 지점 2의 누락 3건은 원인 확인 대상으로 별도 표시합니다. 권한 있는 사용자가 근거 행을 열어 보고 담당자에게 확인하는 흐름을 만든 뒤, 실제 사용성 피드백을 수집합니다.

**구현:** 원천 입력 검증→정규화/격리→키별 최신 상태→지표 SQL→Python 대사→권한 조회 API입니다. 상태 변경이 들어가면 버전 확인·허용 전이·감사 기록을 추가합니다. 큰 데이터 문제는 대표 부하를 측정하기 전부터 분산 시스템을 과하게 넣지 않습니다.

**검증:** 10분/10분 초과/누락/취소/0건 지점, 여러 입금으로 인한 중복, 다른 지점 요청, 동일 배치 재실행을 검사합니다. 실제 지연 감소는 합성 데이터로 주장할 수 없습니다. 도입 후 기준선·관측 기간·사용 여부·외부 변화를 기록해 평가합니다.

**기술 대안:** 첫 단계는 배치+조회 API로 시작할 수 있습니다. 초 단위 대응이 실제 의사결정에 필요하다면 스트리밍을 검토합니다. 오래된 지표라도 화면이 즉시 열리면 충분하다는 가정은 사용자와 확인해야 합니다.

## 3. 모의 질문 24개와 답변 방향

### Q01. DS와 FDSE 중 무엇을 목표로 하며 왜 두 역할을 같이 공부하나요?

답변은 “둘 다 멋있어서”에서 멈추지 않습니다. 문제 정의·사용자 도입을 좋아하는지, 시스템 구현·운영을 깊게 파는지 자신의 실제 경험을 근거로 설명합니다. 이 교재를 사용했다면 같은 KPI에 대해 사용자 메모와 테스트 코드를 작성해 두 역할의 다른 책임을 이해한 경험을 말할 수 있습니다. 아직 선택하지 않았다면 탐색 중임을 솔직히 밝힙니다.

### Q02. 사용자가 AI를 원한다고 하면 곧바로 LLM을 붙이나요?

어떤 결정·반복 업무가 문제인지 확인합니다. 정확한 합계·권한 검사에는 SQL과 결정적 규칙이 더 단순할 수 있습니다. 자연어 검색·설명이 가치가 있는 부분에만 AI를 고려하고 근거·권한·잘못된 응답 처리·평가를 정합니다. 기능 유행보다 사용자 문제에 대한 적합성을 설명합니다.

### Q03. 지연율이 40%인데 지점별 비율 평균은 다른 이유는?

분모가 다르기 때문일 수 있습니다. 전체 지연율은 전체 지연 수/전체 평가 가능 수입니다. 지점 4처럼 분모가 0이면 산출 불가를 0%로 섞지 않습니다. 비율을 평균하려면 무엇을 같은 가중치로 보는 질문인지부터 정의해야 합니다.

### Q04. NULL을 0으로 바꾸면 편하지 않나요?

모름과 0은 다릅니다. 실제 시작 시각이 없는 완료 방문을 지연 0분으로 처리하면 정시였다고 가정하게 됩니다. 의도한 가정이면 별도 지표로 표시할 수 있지만 관측값인 척하면 안 됩니다. COUNT와 분모가 어떻게 바뀌는지도 설명합니다.

### Q05. LEFT JOIN했는데 0건 지점이 사라졌습니다. 어떻게 찾나요?

오른쪽 표의 조건이 WHERE에 있는지 봅니다. 매칭 없는 행의 오른쪽 값은 NULL이므로 조건을 통과하지 못할 수 있습니다. 왼쪽 지점을 보존하려면 JOIN의 ON 조건 또는 조건부 집계를 검토합니다. 작은 지점 2개·방문 1개로 반례를 만들면 설명이 빨라집니다.

### Q06. 청구 합계가 JOIN 뒤 100,000에서 135,000으로 늘었습니다. 원인은?

한 청구에 입금이 여러 개라 청구 행이 반복되었는지 확인합니다. 양쪽 grain과 키 고유성을 먼저 검사합니다. 입금을 invoice_id별로 집계한 뒤 청구와 연결하면 청구 한 행을 유지할 수 있습니다. DISTINCT 금액 합으로 덮으면 같은 금액의 서로 다른 청구가 사라질 수 있습니다.

### Q07. 최신 기록을 고를 때 MAX(timestamp)면 충분한가요?

최신 시각만 얻는 것과 그 시각의 전체 행 하나를 얻는 것은 다릅니다. 같은 시각이 여러 행에 존재할 수 있으므로 순서 규칙을 정합니다. ROW_NUMBER로 키별 시각 내림차순과 안정된 타이브레이커를 사용하되 타이브레이커가 업무 의미를 보장하는지 별도로 확인합니다.

### Q08. NOT IN과 NOT EXISTS를 어떻게 선택하나요?

NOT IN의 하위 결과에 NULL이 있으면 3값 논리 때문에 예상과 달리 아무 행도 선택되지 않을 수 있습니다. “관련 행이 하나도 없다”는 질문에는 상관된 NOT EXISTS가 의도를 명확히 표현하는 경우가 많습니다. 키의 NULL 허용 여부와 작은 반례를 확인합니다.

### Q09. 타임존 문제를 어떻게 예방하나요?

사건 시각을 오프셋이 있는 값으로 받고 저장 기준과 표시 기준을 구분합니다. 날짜 집계에는 업무 시간대를 사용합니다. 날짜 없는 시간, naive datetime, 서로 다른 오프셋의 문자열 비교를 경계합니다. UTC와 서울에서 같은 순간인 입력을 테스트합니다.

### Q10. Python에서 리스트 대신 제너레이터를 쓰면 항상 좋은가요?

전체를 즉시 메모리에 올리지 않아도 되는 순차 처리에 유용합니다. 하지만 일반적인 제너레이터는 한 번 소비하면 끝나고 len이나 임의 인덱싱을 제공하지 않습니다. 재탐색·정렬·전체 집계가 필요한지, 메모리와 오류 발견 시점이 어떻게 달라지는지 비교합니다.

### Q11. 방문마다 직원 목록을 순회하는 코드를 개선해 보세요.

직원 ID로 딕셔너리를 한 번 만들고 방문마다 조회합니다. 평균적인 비용은 O(nm)에서 O(n+m)으로 줄어들 수 있고 색인 메모리는 O(m)입니다. 오른쪽 키가 중복이면 덮어쓰기 오류가 생기므로 N:1 계약을 검사합니다. N:N이면 키마다 목록을 보관하고 출력 크기까지 비용에 포함합니다.

### Q12. BFS는 언제 적절한가요?

연결된 영향 범위를 찾거나 가중치 없는 그래프에서 최소 간선 수 경로를 찾을 때 적절합니다. 큐와 방문 집합을 사용하며 방문 표시는 큐에 넣을 때 합니다. 이동 시간처럼 가중치가 있으면 BFS의 최소 간선 수가 최소 이동 시간과 같지 않을 수 있습니다.

### Q13. async와 await를 초보자에게 설명해 보세요.

async def는 중단·재개 가능한 함수를 정의합니다. 기다릴 일이 실제로 생긴 await에서 현재 코루틴이 잠시 양보하면 이벤트 루프가 실행 가능한 다른 작업을 진행할 수 있습니다. async를 붙였다고 자동 병렬 실행되는 것은 아닙니다. 순차 await와 TaskGroup에 여러 작업을 등록하는 차이를 예제로 보여 줍니다.

### Q14. 비동기 API 안에서 동기 DB 호출을 해도 되나요?

직접 오래 실행하면 이벤트 루프를 막을 수 있습니다. 비동기 드라이버, 스레드 위임, 동기 경로로의 분리 등 실행 모델을 검토합니다. 이 교재의 API는 동기 SQLite 호출을 동기 def 경로에 둔 학습 예입니다. 비동기라는 단어 자체가 성능 보장은 아닙니다.

### Q15. 같은 적재 작업을 다시 실행해도 안전하게 하려면?

업무 키·이벤트 키·버전을 정의하고 입력을 재처리해도 같은 상태가 되도록 설계합니다. 타깃 반영과 진행 위치 기록의 순서·원자성을 확인합니다. 중복·역순·같은 버전 충돌·삭제·부분 실패를 테스트합니다. DB UPSERT 하나만으로 외부 메일이나 결제까지 exactly-once가 되는 것은 아닙니다.

### Q16. 두 사용자가 동시에 같은 배정을 바꾸면?

사용자 흐름에 맞는 버전 비교나 잠금 전략을 제안합니다. 낙관적 잠금이면 읽은 버전으로 UPDATE하고 성공 시 버전을 증가시킵니다. 변경 0행을 성공으로 오해하지 않고 충돌 처리합니다. 잠금을 쓰면 대기·교착·긴 트랜잭션을 관리합니다.

### Q17. API에서 SQL 주입 방지만 하면 안전한가요?

값 바인딩은 사용자 입력이 SQL 코드로 해석되는 위험을 줄이는 방법입니다. 그것만으로 사용자가 다른 지점 데이터에 접근할 권한이 있는지는 판단하지 않습니다. 인증·인가·필요 열 제한·로그·비밀 관리·요청 제한을 구분해 설계합니다.

### Q18. RLS를 켰는데 관리자에게 모든 행이 보입니다. 실패인가요?

실행 역할이 수퍼유저·BYPASSRLS·소유자인지 확인합니다. RLS에는 적용 예외가 있으므로 실제 서비스 역할로 테스트해야 합니다. 표 정책뿐 아니라 API·캐시·내보내기 경로도 점검합니다. 제작 환경에서 이 검증을 안 했다면 설계 설명과 실제 실행 증거를 구분합니다.

### Q19. 쿼리가 느리면 인덱스부터 만드나요?

입력 크기·분포·조건·결과 행 수와 실행 계획을 먼저 확인합니다. 예상/실제 행 차이, 반복, 정렬, 필터와 버퍼를 봅니다. 후보 인덱스의 조회 효과와 쓰기·공간 비용을 비교합니다. 작은 표에서 순차 스캔이 선택되는 것이 반드시 문제는 아닙니다.

### Q20. 데이터가 많아지면 Spark로 바꾸면 되나요?

데이터 크기뿐 아니라 셔플·키 편향·네트워크·직렬화·집계 성질을 봅니다. 합계와 건수는 부분 집계 후 합칠 수 있지만 비율은 분자·분모를 따로 합쳐야 합니다. 로컬 코드가 잘 돌았다고 분산 정확성·성능을 증명한 것은 아닙니다. 실제 규모와 운영 제약이 전환 필요성을 결정합니다.

### Q21. 예측 모델의 성능이 너무 좋으면 무엇을 의심하나요?

판단 시점 이후의 실제 시작 시각·결과 상태·정정 정보가 특징에 섞였는지 확인합니다. 학습/평가 분할과 전처리 fit 범위도 봅니다. 같은 고객·사건이 양쪽에 중복되는지, 시간 순서를 무시했는지도 검사합니다. 높은 숫자 자체보다 재현 가능한 평가 계약이 중요합니다.

### Q22. 시스템을 만들었는데 사용자가 쓰지 않습니다. 무엇을 하나요?

사용자의 실제 작업을 관찰하고 과제를 끝까지 수행하게 해 봅니다. 용어·입력 부담·권한·지연·기존 도구와의 연결 중 어디서 막히는지 기록합니다. 교육 부족으로만 단정하지 않습니다. 더 작은 결정 하나에 집중해 흐름을 수정하고 사용성과 업무 결과를 따로 측정합니다.

### Q23. 모르는 기술 질문을 받으면 어떻게 답하나요?

아는 원리와 확인하지 못한 구현 세부를 구분합니다. 예를 들어 로컬 SQL 결과는 검증했지만 PostgreSQL 동시성 실험은 아직 하지 않았다고 말한 뒤, 두 세션에서 어떤 순서로 어떤 기대 결과를 검증할지 설명합니다. 모르는 API 이름이나 실행 시간을 만들어 내지 않습니다.

### Q24. 이 프로젝트에서 본인이 한 일을 설명해 보세요.

제공된 예제를 실행한 부분, 직접 정의·구현·수정한 부분, 검증한 부분을 나눕니다. 가장 중요한 설계 선택 하나와 버린 대안, 발견한 반례, 사용자에게 전달할 한계를 말합니다. 합성 데이터 실습을 실제 고객사의 운영 성과로 꾸미지 않습니다.

## 4. 코딩 설명 연습: 말하면서 구현하기

문제를 읽고 바로 완성 코드를 암기해 쓰지 않습니다. 입력·출력·빈 입력·중복·오류를 확인하고 작은 예제를 손으로 풉니다. 가장 단순한 알고리즘을 말한 뒤 더 나은 자료구조를 선택합니다. 구현 후 정상·경계·실패 입력을 검증하고 시간·공간 복잡도를 설명합니다.

### 연습 과제 A: 담당자별 방문 수

입력은 방문 목록이고 worker_id가 없을 수 있습니다. 출력은 담당자 ID별 건수입니다. 누락 담당자는 제외할지 별도 미배정으로 셀지 먼저 정합니다. 딕셔너리를 사용하면 한 번 순회해 평균 O(n)으로 집계할 수 있습니다. 빈 입력, 모든 담당자 미배정, 같은 담당자 여러 건을 테스트합니다.

### 연습 과제 B: 키별 최신 상태

입력은 키·버전·상태 이벤트입니다. 키마다 가장 큰 버전을 남기되 같은 버전의 상충 내용을 탐지합니다. 딕셔너리로 현재 최신을 관리할 수 있습니다. 원천 버전 계약이 없는데 단순 문자열 순서가 진짜 최신성을 보장한다고 말하지 않습니다.

### 연습 과제 C: 지점별 지연율 SQL

반드시 branches에서 시작해 0건 지점을 보존합니다. 완료·실제 시각 존재를 분모로 하고 >10을 분자로 합니다. CASE를 중첩하기 전에 각 단계의 grain을 설명합니다. 최종 비율은 분모 0일 때 NULL입니다. SQL-I10과 독립적으로 작성한 Python으로 비교합니다.

## 5. 영어로 설명하는 짧은 틀

문장을 외우기보다 자신의 실제 결과와 연결합니다. 아래 영어는 학습용 표현입니다.

> I first clarified the decision the user needed to make, rather than starting with a dashboard.

처음부터 대시보드를 만들기보다 사용자가 내려야 할 결정을 먼저 확인했다는 뜻입니다.

> The denominator includes completed visits with a known actual start time. Missing timestamps are reported separately.

분모와 결측 처리 규칙을 짧게 설명합니다.

> I verified the same metric independently in SQL and Python and added boundary and authorization tests.

실제 자신이 수행한 검증에만 이 표현을 사용합니다.

> This is a local prototype using synthetic data. Production authentication and PostgreSQL concurrency testing remain separate work.

시제품의 범위와 미완료 검증을 정직하게 설명합니다.

> I chose a simpler batch design first because the required freshness did not justify a streaming system under our stated assumptions.

합의한 신선도 요구가 있을 때만 이런 선택 근거를 말합니다. 실제 사용자의 요구를 확인하지 않았다면 학습 가정이라고 밝힙니다.
