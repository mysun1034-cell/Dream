# Foundry로 연결하는 사고와 Data Scientist 보충 경로

## 1. 로컬 실습과 Palantir 제품 사용 경험을 구분하기

이 교재는 Foundry 계정이나 실행 환경을 제공하지 않습니다. SQLite·PostgreSQL·Python으로 업무 데이터 모델과 운영 문제를 연습한 것입니다. 이 경험을 Foundry에 연결해 설명할 수 있지만, 실제 제품에서 수행하지 않은 작업을 수행했다고 표시하면 안 됩니다.

Palantir 공식 문서는 Ontology를 데이터 자산과 현실의 대상·업무 개념을 연결하는 운영 계층으로 설명합니다. 객체·속성·관계와 함께 Action·함수 등이 업무 흐름을 지원합니다. 단순히 SQL 테이블 이름을 바꾸거나 벡터 DB를 설치하는 것과 같은 개념은 아닙니다. [공식 Ontology 개요](https://www.palantir.com/docs/foundry/ontology/overview/)

## 2. 이 교재의 업무 모델을 연결해 보기

다음 표는 교재가 제안하는 **학습용 대응 설계**입니다. 실제 플랫폼의 기능을 로컬 코드로 완전히 재현했다는 뜻은 아닙니다.

| 업무 의미 | 로컬 학습 표현 | Ontology 관점에서 던질 질문 |
|---|---|---|
| 지점 | branches 행 | Branch 객체의 안정된 식별자는 무엇인가? |
| 담당자 | workers 행 | Worker의 속성과 권한은 무엇인가? |
| 방문 | visits 행 | Visit 객체가 어느 업무 결정을 지원하는가? |
| 고객 | clients 행 | Client의 어떤 속성이 필요한가? 무엇을 공개하면 안 되는가? |
| 담당자가 방문 수행 | worker_id 외래키 | Worker와 Visit의 관계·변경 이력은 어떻게 정의하는가? |
| 지연 판단 | Python 함수·SQL CASE | 같은 업무 규칙을 어떤 경계에서 재사용하는가? |
| 방문 상태 변경 | 조건부 UPDATE·감사 기록 | 누가 어떤 조건에서 Action을 실행하며 실패는 어떻게 보이는가? |
| 확인 대상 목록 | 권한 조회 API | 사용자가 근거를 확인하고 다음 행동을 할 수 있는가? |

표 하나가 언제나 객체 하나와 1:1 대응하는 것은 아닙니다. 원천 데이터가 여러 개여도 같은 업무 대상을 나타낼 수 있고, 분석용 집계 표를 억지로 독립 객체로 만들 필요도 없습니다. 객체를 나누는 기준은 업무 정체성·수명·관계·사용자의 행동입니다.

## 3. 플랫폼으로 옮기기 전 작성할 설계서

**객체 명세:** 이름, 설명, 기본 식별자, 필수/선택 속성, 시간·단위, 원천, 소유자, 변경 규칙을 적습니다. 예를 들어 Visit는 visit_id를 사용하며 실제 시각 누락을 허용하되 품질 상태로 표시합니다.

**관계 명세:** 관계의 양쪽과 카디널리티를 적습니다. Worker 한 명이 여러 Visit를 수행할 수 있지만 미배정 Visit도 존재합니다. 모든 관계가 양쪽에서 항상 존재한다고 가정하지 않습니다.

**Action 명세:** 입력, 검증된 사용자, 허용 상태, 변경 내용, 감사 항목, 충돌·재요청·실패 처리, 사용자에게 보여 줄 결과를 적습니다. 완료 처리 버튼이 보이는 것과 서버에서 변경이 허용되는 것은 다릅니다.

**운영 명세:** 데이터 최신성, 원천 실패 시 동작, 이전 정상 결과 표시, 권한별 검사, 재처리, 이력 재현과 배포/롤백을 적습니다. 동작하는 시제품과 운영 중인 서비스의 차이를 문서화합니다.

### Visit Action의 학습용 계약 예

Action 이름은 ConfirmVisitRecord입니다. 대상은 기록 시각이 누락된 완료 방문입니다. 사용자는 해당 지점의 승인된 운영자여야 합니다. 입력 시각에는 시간대가 있어야 합니다. 요청 시점의 version이 현재 version과 같아야 합니다. 성공 시 실제 시작 시각·version·감사 정보를 같은 트랜잭션에서 변경합니다. 이미 다른 사용자가 수정했다면 덮어쓰지 않고 최신 상태 확인으로 연결합니다.

이 계약은 설계 예이며 제공된 읽기 전용 API에는 구현되어 있지 않습니다. 실제 제품에서 Action을 구현할 때는 해당 환경의 공식 기능·보안 문서를 확인합니다.

## 4. 실제 Foundry 환경에 접근할 수 있을 때의 학습 순서

먼저 합성 데이터만 가져와 원천·정제 데이터와 키·타입을 확인합니다. 다음에는 핵심 업무 객체와 관계를 소수만 모델링하고, 사용자가 근거 행을 찾는 읽기 흐름부터 만듭니다. 그 뒤 별도의 학습 범위에서 Action과 권한 검증을 추가합니다. 변경·신선도·오류가 사용자에게 어떻게 나타나는지 시연합니다.

계정 제공 방식, 접근 가능 기능, SDK, 런타임, 비용·제한은 환경과 시점에 따라 확인해야 합니다. 이 문서는 무료 접근이나 특정 기능의 제공을 보장하지 않습니다. 설치되지 않은 Foundry 패키지를 일반 Python에서 실행할 수 있다고 가정하지 않습니다.

공식 출발점: [Python transforms 개요](https://www.palantir.com/docs/foundry/transforms-python/overview/) · [Ontology 개요](https://www.palantir.com/docs/foundry/ontology/overview/). 본문의 일반 Python 함수는 업무 규칙 연습이며 실제 transform 데코레이터·데이터셋 API와 동일한 실행 모델이 아닙니다.

## 5. 지금 배우는 RAG·에이전트와의 연결

지표 계산과 접근 통제의 정확성은 LLM이 있다고 대신 해결되지 않습니다. 자연어 질문을 허용하는 확장에서는 사용자의 허용 데이터 범위를 서버에서 고정하고, 허용된 조회 도구만 제공하며, 결과와 근거·시점을 연결해야 합니다. 원본 요청 문장에 지점 번호를 적었다고 그 지점 권한을 주지 않습니다.

학습용 확장은 “지점 2의 지연율을 설명해 줘”라는 요청에 이미 검증한 집계와 품질 경고를 넘겨 설명 문장을 만들게 하는 정도로 시작할 수 있습니다. 중요한 숫자와 권한 판단을 모델의 추측에 맡기지 않습니다. SQL/Python으로 정답을 검증하는 기반이 먼저입니다.

AIP나 특정 에이전트 SDK 구현·배포는 이 교재의 실행 범위가 아닙니다. 모델·도구 호출·평가·비용·보안까지 별도로 설계해야 합니다.

## 6. DS가 Data Scientist를 뜻했다면

Data Scientist와 Deployment Strategist는 같은 이름의 역할이 아닙니다. 이 본과정의 SQL·Python·데이터 검증·시점 처리·API·운영은 공통 기반으로 활용할 수 있지만, Data Scientist 목표에는 통계·머신러닝·평가 역량을 별도로 확장해야 합니다. 아래는 **추가 8주 예시 경로**이며 완전한 통계·ML 교과서나 특정 채용 공고를 대체하지 않습니다.

| 보충 주차 | 핵심 개념 | 실제 수행할 연습 | 통과 증거 |
|---|---|---|---|
| 1 | 평균·중앙값·분산·표본·모집단 | 한 극단값을 추가해 평균/중앙값 비교 | 수치와 적절한 요약 선택 이유 |
| 2 | 조건부 확률·기저율·표본 불확실성 | 낮은 사건 비율에서 경보의 정확성 계산 | 분모별 확률을 구분 |
| 3 | 벡터·행렬·내적·표준화 | 특징 행렬과 선형 점수를 손으로 계산 | 행=관측, 열=특징 설명 |
| 4 | 지도학습·회귀·분류·기준 모델 | 훈련 이전 단순 기준선을 정의 | 단순 기준과 복잡한 모델의 비교 |
| 5 | 시간 분할·교차 검증·데이터 누수 | 시점 이후 특징을 제거하고 분할 설계 | 학습/검증/시험의 역할 분리 |
| 6 | 정밀도·재현율·임계값·오류 비용 | 혼동행렬에서 비용과 지표 계산 | 잘못된 양성/음성의 업무 의미 |
| 7 | 전처리 Pipeline·불균형·보정 | 학습 데이터에서만 전처리 fit | 평가 데이터 유출 방지 테스트 |
| 8 | 실험·인과 주장·모니터링 | 도입 평가 설계와 실패 감시 명세 | 성능·사용성·업무 효과를 구분 |

### 보충 실습 A: 경보의 정밀도와 재현율

합성 평가에서 실제 지연을 맞힌 경보 TP=6, 지연이 아닌데 경보를 낸 FP=4, 놓친 지연 FN=3이라고 가정합니다. 정밀도는 경보 중 맞은 비율 6/(6+4)=60%, 재현율은 실제 지연 중 찾은 비율 6/(6+3)≈66.67%입니다. 정확도는 TN 등 전체 수가 없으므로 여기서 계산할 수 없습니다.

```python
# Python 표준 기능만 사용하는 독립 예제

def divide_or_none(numerator: int, denominator: int) -> float | None:
    return None if denominator == 0 else numerator / denominator

tp, fp, fn = 6, 4, 3
print(divide_or_none(tp, tp + fp))
print(divide_or_none(tp, tp + fn))
```

예상 출력은 0.6과 0.6666666666666666입니다. 이 숫자는 모델이 실제로 학습해서 얻은 성과가 아니라 혼동행렬 계산을 위한 가정입니다. 이 보충 코드는 본과정 60강의 예제 실행 집계와 별도입니다.

**변형 문제:** FN을 줄이려고 경보를 많이 내면 정밀도가 항상 좋아질까요? 정답은 아닙니다. TP가 늘어도 FP가 더 많이 늘면 정밀도는 낮아질 수 있습니다. 놓침과 오경보의 비용·사용자의 처리 용량을 함께 봅니다.

### 보충 실습 B: 예측 시점 계약

내일의 방문 지연을 오늘 예측하려면 오늘 시점에 알려진 예정 시각·배정·이전 기록 등을 후보 특징으로 사용합니다. 내일의 actual_start, 완료 여부, 나중에 정정된 배정 결과를 그대로 쓰면 미래 정보가 섞일 수 있습니다.

데이터를 시간 기준으로 학습/검증/시험에 나누고, 전처리의 fit은 학습 부분에서만 수행합니다. 임계값이나 모델 선택을 시험 데이터에 반복 맞추면 독립 평가가 훼손됩니다. scikit-learn은 누수 방지에 Pipeline 사용과 학습/시험 데이터 분리를 강조합니다. [공식 누수·전처리 안내](https://scikit-learn.org/stable/common_pitfalls.html)

본 교재의 24행은 규칙이 반복되는 극소 합성 데이터라 실제 모델 성능 평가에 적절하지 않습니다. 학습 절차를 연습하는 용도와 일반화 성능을 주장하는 용도를 구분합니다. 예측하려는 모집단·시간·고객 집단을 반영한 별도 데이터가 필요합니다.

### 보충 실습 C: 상관과 인과의 차이

시스템 사용 지점의 지연율이 낮아졌다고 바로 시스템이 원인이라고 결론 내리지 않습니다. 인력 변화·업무량·계절·기록 방법이 함께 바뀌었을 수 있습니다. 가능하면 비교 설계와 배정 단위를 미리 정하고, 불가능하면 관측 분석의 한계를 명시합니다. 정책 도입 전후의 단순 차이, 예측 정확도, 실제 업무 효과는 다른 질문입니다.

## 7. SQL·Python 다음에 확장할 FDSE 기초

알고리즘은 해시·BFS·힙에서 이진 탐색·DFS·정렬·동적 계획법으로 넓힙니다. 각 문제에서 입력 계약과 복잡도·반례를 설명합니다. 네트워크에서는 HTTP 요청·응답·타임아웃·재시도, 시스템에서는 프로세스·메모리·파일·동시성, 데이터 시스템에서는 캐시·큐·일관성·복구를 확장합니다.

UI가 필요한 프로젝트는 최소한 사용자가 판단하고 행동하는 화면을 구현합니다. TypeScript나 다른 언어의 선택은 요구사항과 지원 직무를 보고 결정합니다. 여기서 배우지 않은 기술을 전부 안다고 표현하지 말고, 핵심 개념을 새 도구로 옮겨 검증하는 능력을 보여 줍니다.
