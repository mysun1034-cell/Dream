## Q29. Ch.2-03 — 결측치 처리 · 원-핫 인코딩 · Pipeline `#ch02` `#N12`

### A.

**책:** 02-3 · 노드 **N12** (Ch.2 데이터 다루기 마무리)

> ⚠️ 최초 설명에서 "imputer.fit(train)까지 포함한 순서를 02-2에서 배웠다"고 잘못 말했다가 정정함.
> **02-2(Q28)의 순서에는 imputer가 없었음** — imputer는 여기 02-3에서 처음 나온 새 단계.

#### 1) 결측치(Missing Value) — 빈칸이 있는 데이터

| 상황 | 예 |
|---|---|
| **EDENING** | 학생이 특정 문제를 안 풀어서 `풀이시간` 칸이 비어있음 |
| **케어링크** | 이용자 `생년월일`이 등록 누락 |

sklearn 모델 대부분은 **NaN(빈칸)을 그대로 못 받습니다.** 셋 중 하나를 골라야 합니다.

| 전략 | 방법 | 언제 |
|---|---|---|
| **제거** | `dropna()` — 그 행/열 통째로 버림 | 빈칸이 아주 적을 때 |
| **대체(imputation)** | 평균·중앙값·최빈값으로 채움 | 보통 이걸 씀 |
| **표시 후 대체** | 채우고 "원래 비어있었다"는 열 하나 추가 | 빈칸 자체가 의미 있을 때 |

```python
from sklearn.impute import SimpleImputer

imputer = SimpleImputer(strategy="mean")   # 평균으로 채움
X_train_filled = imputer.fit_transform(X_train)   # ★ fit도 train만
X_test_filled  = imputer.transform(X_test)
```

**02-2에서 배운 규칙(fit은 train만, transform은 둘 다)이 여기도 그대로 적용됩니다.**
평균을 test까지 포함해서 구하면 여기서도 **data leak**입니다.

#### 2) 원-핫 인코딩 — 글자를 숫자로 (범주형 변수)

k-NN·회귀 같은 모델은 **숫자만** 계산합니다. `"도미"`, `"빙어"` 같은 **글자 라벨**이나
`"서울"`, `"부산"` 같은 **범주형 feature**는 그대로 못 넣습니다.

**나쁜 방법 — 그냥 숫자로 치환:** 서울=0, 부산=1, 대구=2 …

| 문제 | 왜 |
|---|---|
| 순서가 생겨버림 | 모델이 "대구(2)가 서울(0)보다 크다"로 오해 |
| 거리 왜곡 | k-NN 거리 계산에서 엉뚱한 차이가 생김 |

**원-핫 인코딩 — 항목마다 열을 하나씩:**

| 원본 | 서울 | 부산 | 대구 |
|---|---|---|---|
| 서울 | 1 | 0 | 0 |
| 부산 | 0 | 1 | 0 |
| 대구 | 0 | 0 | 1 |

"하나만 뜨겁다(1)"라서 one-hot입니다. 순서 정보가 없어져서 왜곡이 안 생깁니다.

```python
import pandas as pd
pd.get_dummies(df["지역"])          # pandas로

from sklearn.preprocessing import OneHotEncoder
OneHotEncoder().fit_transform(X[["지역"]])   # sklearn으로 (train만 fit)
```

#### 3) Pipeline — 순서를 코드로 못 박기

```text
split → imputer.fit(train) → scaler.fit(train) → transform → model.fit
```
(imputer가 scaler보다 앞 — 결측치부터 채우고 스케일링)

이 순서를 매번 손으로 다시 짜면 실수하기 쉽습니다(train/test 섞어서 fit하는 실수 등).
`Pipeline`은 이 단계들을 **하나의 객체로 묶어서** 실수를 원천 차단합니다.

```python
from sklearn.pipeline import Pipeline
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import StandardScaler
from sklearn.neighbors import KNeighborsClassifier

pipe = Pipeline([
    ("imputer", SimpleImputer(strategy="mean")),
    ("scaler", StandardScaler()),
    ("model", KNeighborsClassifier(n_neighbors=3)),
])

pipe.fit(X_train, y_train)      # 세 단계가 순서대로 train에만 fit됨
pipe.predict(X_test)            # test는 자동으로 transform만 됨 (fit 안 됨)
```

#### 4) 오늘 한 표로 정리

| 문제 | 도구 | 규칙 |
|---|---|---|
| 빈칸 | `SimpleImputer` | fit은 train만 |
| 글자 범주 | `OneHotEncoder` / `get_dummies` | 순서 정보 안 생기게 |
| 순서 실수 | `Pipeline` | 한 객체로 묶어서 leak 원천 차단 |

#### 5) 도메인 연결

| | 결측 | 원-핫 |
|---|---|---|
| **EDENING** | 안 푼 문제 → 평균 풀이시간 대체 or "미응시" 플래그 | 학년(1~6)은 순서 있으니 원-핫 대신 숫자 그대로가 나을 수도 |
| **케어링크** | 생년월일 누락 → 별도 "결측여부" 플래그 열(나이는 청구 자격에 쓰이니 함부로 평균 대체 위험) | 등급(1~5등급)도 순서 있어 원-핫 대신 숫자 유지 고려 |

**★함정 확인:** 순서가 있는 범주(학년·등급)를 원-핫으로 무조건 바꾸는 게 항상 정답은 아님 — 순서 정보를 살리고 싶으면 그냥 숫자로 두는 게 나을 때도 있음.

#### 확인 3문

1. `imputer.fit()`을 test 데이터에도 하면 왜 안 되나?
2. "서울=0, 부산=1"처럼 직접 숫자를 매기면 어떤 문제가 생기나?
3. `Pipeline`을 쓰면 어떤 실수가 구조적으로 막히나?

**힌트:** 1→leak(02-2와 같은 이유) / 2→없던 순서·거리 왜곡이 생김 / 3→train/test 섞어서 fit하는 실수

## Q30. "split → scaler.fit(train) → transform(train, test) → model.fit → predict(test)" 순서를 자세히 풀어달라 `#ch02` `#N10` `#N11`

### A.

**한 줄:** 이 다섯 단계는 전부 하나의 원칙을 지키기 위한 순서입니다 — **"test는 끝까지 아무것도 모르는 상태로 남겨둔다."**

#### 1) 왜 순서가 이렇게 정해졌나

02-2(Q28)에서 "test = 모의고사"라고 했다. 모의고사의 조건은 **문제를 만드는 사람도, 채점 기준을 정하는 사람도 시험 볼 사람의 답안을 미리 보면 안 된다**는 것. 이 다섯 단계는 그 조건을 코드로 강제하는 절차.

#### 2) 단계별로 뜯어보기

**① `split`** — 원본 데이터를 train/test로 쪼갠다. 이 순간부터 test는 **봉인**된다.

```python
X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.25, random_state=42)
```

**② `scaler.fit(train)`** — **train 데이터만** 보고 평균(μ)과 표준편차(σ)를 계산.

```python
scaler = StandardScaler()
scaler.fit(X_train)     # X_test는 아예 등장하지 않음
```

이 시점에 `scaler.mean_`, `scaler.scale_`이 저장됨. **"잣대의 눈금"**.

**③ `transform(train, test)`** — 그 눈금(train의 μ,σ)을 **train과 test 둘 다에** 적용.

```python
X_train_s = scaler.transform(X_train)   # train도 같은 눈금으로
X_test_s  = scaler.transform(X_test)    # test도 같은 눈금으로 — test 것으로 새로 재지 않음
```

헷갈리는 지점: "test에도 적용하는데 왜 leak이 아니냐?" → **적용(transform)은 되지만, test 값이 눈금을 만드는 데는 안 쓰였기 때문.** 눈금(μ,σ)은 이미 ②에서 train만으로 확정됐고, ③은 그 눈금을 그대로 읽기만 함.

**④ `model.fit(train)`** — 스케일링된 train으로만 모델 학습. (Ch.1부터 계속 나온 규칙과 동일)

**⑤ `predict(test)`** — 학습 끝난 모델에 test를 딱 한 번 넣어 채점. 결과 보고 다시 ②·③·④로 돌아가서 손보면 안 됨(Ch.5 검증세트가 할 일).

#### 3) 숫자로 직접 보기 — 왜 순서가 틀리면 진짜 문제가 생기는지

무게(g) 데이터 5개, train 3개 + test 2개.

| | 무게 |
|---|---|
| train | 100, 200, 300 |
| test | 250, 500 |

**✅ 올바른 순서 (train만으로 눈금)**

```
μ = (100+200+300)/3 = 200
σ ≈ 81.6   (train 3개만으로 계산)
```

이 눈금으로 test를 재면:
```
250 → (250-200)/81.6 ≈ 0.61
500 → (500-200)/81.6 ≈ 3.68
```

**❌ 잘못된 순서 (전체 5개로 눈금 — split 전에 스케일링)**

```
μ = (100+200+300+250+500)/5 = 270
σ ≈ 132.7   (test 값 250, 500이 눈금 계산에 껴버림)
```

**뭐가 문제냐:** 잘못된 방식에서는 **train 데이터(100,200,300)를 스케일링한 결과값 자체가 달라진다** — 눈금이 270/132.7 기준으로 바뀌었으므로. 모델은 이 "test를 살짝 엿본 눈금"으로 재조정된 train 값을 보고 학습한다. 즉 모델 파라미터 안에 **test의 흔적이 간접적으로 스며든다.** 그 상태에서 test로 채점하면 실제보다 **점수가 잘 나온다** — 실전(진짜 새 데이터)에서는 그 좋은 점수가 재현이 안 됨.

#### 4) 비유

> **잣대(자)의 눈금은 참고서(train)만 보고 새긴다.** 그 자로 참고서도 재고 시험지(test)도 잰다.
> 시험지를 먼저 들여다보고 눈금을 새기면, 그 잣대로 잰 시험 점수는 못 믿는다.

#### 5) 자주 하는 실수 3가지

| 실수 | 무엇이 문제 |
|---|---|
| **split 전에 전체 데이터로 `scaler.fit`** | 방금 숫자로 본 것. 가장 흔한 leak |
| **train과 test를 각각 따로 `fit`** | 눈금이 두 개 생김 — 모델이 학습한 눈금과 test를 잰 눈금이 달라 비교 자체가 무의미 |
| **test 성능 보고 다시 튜닝** | test는 "1회용 모의고사". 다시 보고 고치면 그건 이미 참고서가 된 것(검증세트의 역할) |

#### 6) 전체 표

| 단계 | train | test | 이유 |
|---|:---:|:---:|---|
| split | ✓ | ✓ | 여기서부터 test 봉인 |
| scaler.fit | ✓ | ✗ | 눈금은 train만 보고 새김 |
| scaler.transform | ✓ | ✓ | 눈금 적용은 둘 다 — 적용≠학습 |
| model.fit | ✓ | ✗ | 모델도 train만 보고 학습 |
| model.predict | (선택) | ✓ | test는 최종 채점 1회 |

#### 7) 도메인 연결

| | 잘못하면 |
|---|---|
| **EDENING** | 학생 A~E(train) 풀이시간 평균으로 "빠름/느림" 기준을 만들어야 하는데, 신규 학생 F(test) 기록까지 섞어서 기준을 만들면 → 모델이 F를 "적당히 잘 맞히는" 것처럼 보이지만 실제 신규 학생한테는 안 통함 |
| **케어링크** | 기존 이용자(train) 청구액 통계로 "이상 거래" 기준선을 잡아야 하는데, 검증하려는 신규 이용자(test) 청구액까지 기준선 계산에 넣으면 → 이상탐지가 신규 이용자를 놓칠 수 있음 |

#### 확인 3문

1. `scaler.transform(X_test)`는 하는데 왜 `scaler.fit(X_test)`는 안 하나?
2. train 3개(100,200,300)를 올바른 방식과 잘못된 방식으로 스케일링하면 같은 데이터인데도 결과값이 다르다. 왜?
3. test 점수가 낮게 나와서 스케일러를 test까지 포함해 다시 fit했다면, 이게 왜 문제인가?

**힌트:** 1→fit은 "학습"이라 train만, transform은 "적용"이라 둘 다 / 2→눈금(μ,σ) 자체가 어떤 데이터로 계산했느냐에 따라 달라지므로 / 3→test 성능을 보고 손댄 순간 test가 더 이상 "안 본 시험"이 아니게 됨(정보 유출)

## Q31. 왜 하필 평균(μ)과 표준편차(σ)를 계산하나 `#ch02` `#N11`

### A.

**한 줄:** μ는 "기준점(0)을 어디로 잡을지", σ는 "한 칸의 크기를 얼마로 잡을지"를 정한다. 이 둘이 있어야 서로 다른 단위의 feature를 같은 자로 잴 수 있다.

#### 1) 문제로 돌아가서 (Q28 복습)

| | 차이 | k-NN 거리 기여 |
|---|---|---|
| 길이 3cm 차 | 3 | √9 = **3** |
| 무게 50g 차 | 50 | √2500 = **50** |

무게가 길이보다 17배 더 크게 거리에 반영됨. 이걸 고치려고 μ, σ를 계산.

#### 2) σ(표준편차) — 진짜 문제를 푸는 건 이쪽

σ로 나누면 "cm", "g" 같은 단위 자체가 사라지고, "이 feature 안에서 이 값이 얼마나 흔한가/특이한가"라는 공통 단위로 바뀐다.

```
길이: σ가 5cm라면 → 3cm 차이는 "0.6칸 차이"
무게: σ가 100g라면 → 50g 차이는 "0.5칸 차이"
```

→ 둘 다 "칸(표준편차) 단위"로 재니까 공정하게 비교됨. 이게 σ로 나누는 이유.

#### 3) 그럼 μ(평균)는 왜 빼나 — 재밌는 지점

**k-NN만 놓고 보면 μ를 안 빼도 방금 그 문제는 해결된다.** 거리는 두 점의 *차이*만 보는데, 모든 점에서 똑같이 μ를 빼도 두 점 사이의 차이는 안 바뀐다.

```
100 - 90 = 10
(100-50) - (90-50) = 50 - 40 = 10   ← 똑같음
```

**그런데 왜 항상 같이 하냐면**, `StandardScaler`가 k-NN 전용이 아니기 때문.

| 나중에 배울 것 | μ를 안 빼면 생기는 문제 |
|---|---|
| Ch.3 Ridge/Lasso (규제 회귀) | 규제가 계수마다 다르게 걸려서 왜곡됨 |
| Ch.6 PCA | "가장 많이 퍼진 방향"을 찾아야 하는데 평균이 0이 아니면 방향 자체가 엉뚱해짐 |
| Ch.7 신경망 | 학습이 느려지거나 불안정해짐 |

k-NN엔 있으나 없으나 무관하지만, 뒤에 나올 모델들엔 꼭 필요해서 처음부터 습관으로 같이 함.

#### 4) 표로 정리

| | 하는 일 | k-NN엔 | 나중(회귀·PCA·신경망)엔 |
|---|---|---|---|
| **μ 빼기** (centering) | 기준점을 0으로 옮김 | 있으나 없으나 무관 | **필수** |
| **σ 나누기** (scaling) | 한 칸 크기를 통일 | 바로 이게 원래 문제 해결 | 필수 |

#### 5) 참고 — 다른 자도 있다

평균·표준편차 대신 최소·최대로 0~1 사이에 맞추는 `MinMaxScaler`, 이상치에 강한 중앙값·사분위수 기반 `RobustScaler`도 있음. 지금은 가장 기본형인 표준화(z-score)만 하는 것.

#### 확인 2문

1. k-NN만 쓸 거라면 μ를 안 빼도 결과가 똑같을까?
2. σ로 나누는 걸 빼먹으면 어떤 feature가 거리를 지배하게 되나?

**힌트:** 1→예, k-NN 거리는 평행이동에 영향 안 받음(단 습관은 들여두는 게 좋음) / 2→값의 범위(스케일)가 큰 feature

**다음 노드:** N13~N19 — **Ch.3 회귀** (선형회귀·다항회귀·Ridge/Lasso) 시작
